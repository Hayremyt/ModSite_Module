# ModsSite — модуль веб-панели модов для GravitLauncher 5.7.x

> **English version of this README: [../README.md](../README.md)**

Модуль для LaunchServer, добавляющий **веб-панель управления модпаками
профилей** с загрузкой и обновлениями с **Modrinth** и **CurseForge**:

- **ресурспаки и шейдеры — полноправные жители**: папки профилей
  `resourcepacks` / `shaderpacks`, собственные записи модпаков
  (`kind: "mod" | "resourcepack" | "shader"`), поиск по каждому типу на
  Modrinth/CurseForge и полный конвейер — установка/обновления/
  опциональность/группы/зависимости; фильтр типа на вкладке «Моды» и выбор
  типа в поиске (тип по умолчанию настраивается в Настройки → Обновления или
  отдельно для каждого браузера);
- **система предложений**: наблюдатель находит проект в поиске и жмёт
  «Предложить»; админ видит очередь на вкладке «Предложения» (кто, что, в
  какой профиль, какого типа) с фильтрами по имени/пользователю и типу — и в
  один клик скачивает его в модпак или отклоняет; лимит «в ожидании» на
  пользователя и список логинов, отстранённых от предложений, настраиваются;
  наблюдатели видят свои предложения и остаток лимита;
- выбор и настройка **опциональных модов**, **зависимостей** и **конфликтов**;
- **опциональные моды для игроков**: автоматическая синхронизация с
  `updateOptional` профиля — чекбоксы в диалоге «Настройки» лаунчера, с
  автоматическим обновлением привязки файла при смене его имени (см. «Как
  это устроено»);
- **обновления с переименованием файлов** — старый файл отслеживается по
  сохранённому имени и корректно удаляется (в том числе у опциональных);
- **импорт существующих jar** — файлы, положенные в папку модов вручную,
  распознаются в модпаке по хэшам Modrinth (SHA-1) и отпечаткам murmur2
  CurseForge, без повторного скачивания; если хэш не совпал (автор пересобрал
  jar), мод узнается резервным поиском по modId из jar с SHA-1-проверкой
  файлов версий;
- **вкладка «Поиск» с фильтрами как в Modrinth/Prism**: категории, загрузчики
  (Fabric/Forge/NeoForge/Quilt), версия игры, сортировка (релевантность/
  скачивания/подписки/новизна/обновлённые) и пагинация;
- **фильтры, поиск и сортировка на вкладке «Моды»**: отдельные чипы
  «Опциональные» и «Обновления» (сочетаются), отдельное меню сортировки —
  по умолчанию / А-Я / Я-А (запоминается в браузере) — и живой поиск по
  УСТАНОВЛЕННЫМ модам (имя/файл/id, без обращений к API);
- **загрузчик модпака по умолчанию**: селектор в мета-чипах вкладки «Моды»
  (Авто/Любой/Fabric/Forge/NeoForge/Quilt) — автоматически применяется к
  поиску и проверкам обновлений, можно переопределить на каждый поиск;
- **приоритет источников обновлений**: Настройки → Обновления — порядок
  Modrinth/CurseForge меняется кнопками ↑↓; проверки идут по порядку: если
  мода на источнике нет (проект удалён, источник недоступен, нет метаданных),
  файл ищется по хэшу на следующем, а файл, найденный на более приоритетном
  источнике, перепривязывает мод к нему. «Проверить обновления» также
  ГЕНЕРИРУЕТ метаданные для «локальных» модов (сопоставление SHA-1/murmur2);
- **кнопка «Отложить» у каждого мода**: отложенная версия не ставится — ни
  сама по себе, ни через «Обновить всё» — пока не выйдет более новая; новая
  версия снимает отсрочку;
- **«Перезагрузить профили»** — перечитывает конфиги профилей
  (profiles/*.json) с диска без рестарта: ручные правки `updateOptional`,
  `modsLoader` и т.п. вступают в силу немедленно; моды, чьи файлы привязаны
  в `updateOptional` — ВКЛЮЧАЯ нестандартные формы profile.json
  (`optionalMods[].list` и т.п., которые сам лаунчер игнорирует) и совпадения
  имён записей — автоматически становятся опциональными при открытии списка;
  диагностика через `mods profile optionals`;
- кнопка **«Обновить хэши»** — пересчитывает HashedDir профиля (то же, что
  `sync`);
- **гибридная авторизация**: локальные учётки из конфига + учётки лаунчера
  (распознавание админов по правам лаунчера или собственному SQL-запросу,
  например к колонке `isAdmin`);
- **защита от перебора**: баны IP с эскалирующими длительностями, баны
  логинов, белый/чёрный списки (консольные команды + панель), rate limiting,
  TOTP 2FA, аудит;
- работает по **HTTP и HTTPS** (флаг cookie `Secure` — автоматически);
- интерфейс: **русский/английский**, без CDN и внешних ресурсов;
- **шесть встроенных тем — у каждой светлая и тёмная версии** — плюс
  кастомные темы, задаваемые админом (см. «Темы»); дизайн по умолчанию —
  glassmorphism (тёмный тех + сигнальный зелёный, светящиеся блобы на фоне,
  полупрозрачные стеклянные карточки, SVG-иконки без эмодзи, адаптивная
  вёрстка, фокус-кольца, поддержка `prefers-reduced-motion`).

Протестировано на **LaunchServer v5.7.13** (живой прогон: вход, TOTP, баны за
перебор, поиск/добавление/обновление модов, каталог с фильтрами,
фильтры/поиск/сортировка и «Отложить», настройки и приоритет источников,
загрузчик модпака, усыновление опциональности из updateOptional — включая
нестандартные формы profile.json (`optionalMods[].list`), перезагрузку
профилей, переименования файлов, импорт существующих jar, пересчёт хэшей,
типы контента и систему предложений, темы со светлыми/тёмными вариантами и
управление кастомными темами, уровни логов в консоли; автоматические
проверки: 430 smoke, 27+ live API/браузерных — все зелёные).

## Требования

| Компонент | Версия |
|---|---|
| LaunchServer (GravitLauncher) | **5.7.x** (тестировалось на 5.7.13) |
| Java (сборка и запуск) | **21+** |
| Интернет с сервера | до `api.modrinth.com` (и `api.curseforge.com`, если используется) |

## Сборка

Единственный вариант сборки — Gradle Wrapper с указанием пути к вашей сборке
LaunchServer:

```bash
cd ModsSite_module
./gradlew build -PlaunchserverDir=/путь/к/LaunchServer     # Linux/macOS
gradlew.bat build -PlaunchserverDir=C:\путь\к\LaunchServer  # Windows
```

Ставить Gradle не нужно — `gradlew` сам скачает Gradle 8.10.2, а если не
найдётся подходящий JDK 21, скачает и его (foojay). Путь указывает на
РАСПАКОВАННЫЙ `LaunchServerBuild.zip` из
[релиза GravitLauncher](https://github.com/GravitLauncher/Launcher/releases)
— нужна его подпапка `lib`. Чтобы не передавать путь каждый раз, задайте его
один раз в `gradle.properties` (`launchserverDir=...`).

> Примечание: тулчейн — Java 21, как и сам LaunchServer 5.7.x. Jar'ы
> LaunchServer собраны байткодом v65, который более старые javac прочитать не
> могут — это одна из типичных причин «gradle build падает».

Готовый jar: `build/libs/ModsSite_module.jar`.

В дистрибутивном zip уже лежит **собранный и протестированный**
`ModsSite_module.jar` (на 5.7.13) — если исходники не меняются, сборку можно
пропустить вовсе.

### GitHub Actions: сборка по кнопке и релизы

В исходниках лежит `.github/workflows/build.yml` — кроме пуша репозитория на
GitHub ничего настраивать не нужно:

1. Вкладка **Actions** -> **Build & Release** -> **Run workflow**.
2. Оставьте `release_tag` пустым — будет только сборка; `ModsSite_module.jar`
   и дистрибутивный zip появятся в **Artifacts** прогона.
3. Укажите `release_tag` = `v1.1.1` — тогда прогон дополнительно опубликует
   GitHub Release с обоими файлами; тег при отсутствии создаётся сам.
4. Пуш тега `v*` делает то же самое без кнопки.

Откуда CI берёт jar'ы LaunchServer? Скачивает `LaunchServerBuild.zip` из
релизов GravitLauncher
(`https://github.com/GravitLauncher/Launcher/releases/latest/download/LaunchServerBuild.zip`,
кэшируется по тегу релиза; конкретный релиз задаётся входом `ls_release`) и
распаковывает рядом с проектом — та же папка `lib`, что нужна и локальной
сборке, поэтому коммитить LaunchServer в репозиторий не требуется.

Встроены две проверки: тег релиза обязан совпадать с версией модуля
(`v1.1.1` <-> `version = "1.1.1"` в `build.gradle.kts`, иначе прогон падает с
подсказкой), а после сборки каждый прогон проверяет jar (главный класс,
`Module-Main-Class` в манифесте, наличие разбора `totalCount` CurseForge в
байткоде) и печатает его SHA-256 в лог.

## Установка

1. Скопируйте `ModsSite_module.jar` (готовый из дистрибутивного zip или свой
   `build/libs/ModsSite_module.jar`) в папку `modules/` LaunchServer.
2. Добавьте модуль в `modules.json` (в корне LaunchServer):

```json
{
  "loadModules": ["ModsSite_module"],
  "loadLauncherModules": []
}
```

(если список `loadModules` уже есть — просто допишите `"ModsSite_module"`)

3. Запустите LaunchServer. При первом старте модуль:
   - создаст `config/ModsSite/Config.json` с настройками по умолчанию;
   - создаст **локальную учётку `admin` со случайным паролем** — пароль один
     раз печатается в консоль и в лог:
     `FIRST START — web login created (shown ONCE): login: admin, password: XXXX`;
   - откроет сайт по пути `/mods`.

4. Немедленно смените пароль: `mods user pass admin НовыйПароль`
   (или в конфиге).

Сайт: `http://<адрес-лаунчера>:9274/mods/`. Если у сервера есть домен
(например, `mods.example.com`), сайт может открываться и в корне домена —
`http://mods.example.com/` — и даже по обоим адресам одновременно: добавьте
домен в `web.siteDomains` (вкладка «Настройки» → «Домены сайта») — рестарт не
нужен (см. «HTTP и HTTPS» → «Один сайт, два адреса»).

#### Файлы веб-интерфейса в конфиге (config/ModsSite/web)

Файлы интерфейса (`index.html`, `style.css`, `app.js`, `i18n.js`,
`favicon.svg`) хранятся НЕ в jar, а в `config/ModsSite/web/` — при старте
модуль сам записывает их туда и раздаёт с диска. Чтобы поменять внешний вид,
достаточно отредактировать файл и перезагрузить страницу (`Ctrl+F5`):
рестарт не нужен.

Модуль поддерживает набор файлов в согласованном состоянии при каждом старте:
- файла нет (удалили/потерялся) — восстанавливается из jar;
- файл не менялся админом, а версия модуля выросла — обновляется до нового;
- файл менялся админом — правка сохраняется, файл не трогается;
- файла нет нигде (ни на диске, ни в jar) — в лог пишется ERROR с именами
  файлов.

Принудительно перезаписать ВСЁ из jar (локальные правки будут потеряны):
`mods web restore`. Статус файлов: `mods web`.

Аварийный случай «jar без web/» лечится тем же механизмом: распакуйте
`web/*` из дистрибутивного zip в `config/ModsSite/web/` — интерфейс оживёт
без замены jar.

## Быстрый старт

1. Войдите (`admin` + пароль из лога; если включён TOTP — код из приложения
   аутентификатора).
2. Сверху — вкладки профилей LaunchServer (модпак = профиль).
3. Ищите моды: вкладка «Поиск» — выберите источник (Modrinth/CurseForge),
   наберите имя, нажмите «Искать», добавьте нужное (фильтры — чипы
   «Опциональные»/«Обновления»; поиск по установленным и сортировка живут на
   вкладке «Моды»; загрузчик и версия игры подставляются из профиля).
   - Зависимости привязываются автоматически; недостающие будут предложены.
4. Чекбокс «Опциональный» на карточке делает мод опциональным (игрок сможет
   отключить его у себя в лаунчере) или обязательным для всех. Переключателей
   вкл/выкл больше нет — скачано значит нужно: весь модпак и есть состав.
   Конфликтующие моды уживаются мирно; лаунчер просто не даст игроку включить
   оба сразу (сайт лишь предупреждает и подсвечивает).
5. **«Применить состав»** — скачивает недостающие файлы и синхронизирует
   `updateOptional` профиля со составом («выключенных» модов больше нет).
6. **«Проверить обновления»** — обновляет информацию о модах И проверяет
   источники на свежие версии (не нужна конкретная версия? кнопка
   **«Отложить»** у мода). **«Обновить всё»** обновляет ТОЛЬКО то, что нашла
   проверка (плюс моды с отсутствующим файлом) — актуальные моды заново
   не перекачивает. Пока идёт обновление, обе кнопки просто открывают окно
   статуса бегущей задачи.
7. **Окно статуса** показывает по каждому модулю статус и байты и содержит
   кнопку **«Остановить»**: начатые скачивания докачиваются, не начатые —
   отменяются и из очереди исчезают. Если посреди обновления закрыть или
   перезагрузить страницу, окно откроется само (задача живёт на сервере).
8. **«Обновить хэши»** — принудительный пересчёт хэшей профиля, после чего
   клиенты лаунчера при следующем запуске синхронизируют файлы (скачают новые
   и **удалят устаревшие**, включая старые версии модов).
9. Порядок проверки обновлений (Modrinth/CurseForge), число **одновременных
   скачиваний** и **таймаут ответа источника** — на вкладке **«Настройки»**;
   если правили profiles/*.json руками — кнопка **«Перезагрузить профили»**.

## Интерфейс и темы

### Темы

Каждая тема существует в **двух вариантах — светлом и тёмном**. Переключатель
палитры (солнце/луна) стоит прямо в меню темы; выбор темы и варианта хранится
в браузере (`localStorage`), применяется до первой отрисовки (без вспышки
«не той» темы) и переживает перезагрузки. Работают и демо-ссылки:
`?theme=terminal&mode=light`.

Шесть встроенных тем:

| Тема | Вид |
|---|---|
| **Glass** (по умолчанию) | тёмное стекло, зелёный акцент, светящиеся блобы на фоне; светлый вариант — воздушное бело-голубое стекло |
| **Comic** | полутоновая бумага, жирные чёрные обводки, плоские печатные тени; тёмный вариант — «ночной выпуск» с кремовыми чернилами |
| **Simple** | светлый минимализм без эффектов; тёмный вариант — строгая тёмно-серая гамма |
| **Neon** | тёмный киберпанк с циано-розовым свечением; светлый вариант — «дневной synthwave», белый с неоном |
| **Pixel** | майнкрафтовый вкус: шахматный фон, нулевые радиусы, жёсткие блочные тени, моноширинный шрифт; светлый вариант — «8-битное утро» |
| **Terminal** | зелёный CRT-терминал со строчной развёрткой и мигающим курсором; светлый вариант — «бумажный терминал» |

Кастомные (заданные админом) темы добавляются так же и тоже имеют светлый и
тёмный вариант — см. [Как сделать свои темы](#как-сделать-свои-темы).

Управление темами (только админ, Настройки → **Оформление**):

- **Тема по умолчанию** и **вариант по умолчанию** — что видят пользователи
  без личного выбора (личный выбор всегда важнее);
- **Встроенные темы** вкл/выкл — выключенная тема скрыта у ВСЕХ: у игроков,
  наблюдателей и админов одинаково (хотя бы одна тема обязана остаться
  доступной);
- **Кастомные темы** — добавляйте и удаляйте свои: имя, шрифт (обычный/
  моноширинный), стиль углов (прямые/мягкие/круглые) и по семь цветов на
  каждый вариант (фон, карточки, текст, приглушённый текст, границы, акцент,
  второй акцент) — все остальные тона интерфейса выводятся автоматически.
  У формы добавления есть **живой предпросмотр**: весь сайт перекрашивается
  по ходу выбора цветов. До 16 кастомных тем; доступны всем ровно как
  встроенные.

Кто что может:

- **игрок / наблюдатель** — выбирает любую из доступных тем и вариант
  светлый/тёмный; выбор личный и хранится в его браузере;
- **админ** — то же самое, плюс управление: тема/вариант по умолчанию,
  выключение встроенных, добавление/удаление кастомных тем.

Конфигурация тем отдаётся в браузер самим модулем как крошечный динамический
`/theme.js` (доступен до входа, никогда не кэшируется) — поэтому любое
изменение админом доходит до каждого посетителя при следующей загрузке
страницы.

Вёрстка адаптивна — от телефонов 390px до широких мониторов (поля и кнопки
во всю ширину, ничего не вылезает), все иконки — инлайн-SVG, язык интерфейса
(русский/английский) переключается одним кликом.

### Как сделать свои темы

Три уровня — от «вообще без кода» до полностью самодельного дизайна.

#### 1. В панели — из базовых цветов, без кода

Настройки → **Оформление** → **«Добавить тему»**:

1. введите **название** (до 40 символов) — id темы сгенерируется из него
   автоматически;
2. выберите **шрифт** (обычный / моноширинный) и **стиль углов**
   (прямые / мягкие / круглые);
3. задайте **семь цветов светлого варианта**: фон, карточки, текст,
   приглушённый текст, границы, акцент, второй акцент;
4. задайте **семь цветов тёмного варианта** — те же ключи.

Пока вы подбираете цвета, весь сайт перекрашивается **вживую** (предпросмотр),
а переключатель солнце/луна мгновенно показывает оба варианта. «Добавить»
кладёт тему в список; **«Сохранить настройки»** отправляет её на сервер —
после этого она появляется в меню тем у КАЖДОГО посетителя, как встроенная.
До 16 кастомных тем; удаление — иконка корзины в списке + «Сохранить
настройки».

Все остальные тона интерфейса (наведения, тени, бейджи, тосты, фокус-кольца)
**выводятся автоматически** из этих семи цветов — навыки дизайнера палитр не
нужны.

Тот же список можно править руками в `config/ModsSite/Config.json` →
`themes.custom` (пример есть в «Конфигурации»); сервер сам валидирует id,
цвета (`#rrggbb`) и лимит в 16 тем.

#### 2. Полностью свой дизайн — свои фоны и эффекты

Веб-интерфейс — это обычные редактируемые файлы на диске:
`config/ModsSite/web/` (`index.html`, `style.css`, `app.js`, `i18n.js`).
Отредактировали файл — перезагрузили страницу (`Ctrl+F5`); рестарт сервера не
нужен, а файлы, изменённые руками, модуль **никогда не перезаписывает**
(статус: `mods web`; сброс всего на заводское: `mods web restore`).

Тема, добавленная через панель, получает атрибут страницы
`data-theme="c-<id>"` (префикс `c-` означает кастомную тему). Поэтому рецепт
полностью своего вида такой:

1. **Базу добавьте через панель** (способ 1) — назовите, скажем, «Ночная
   вишня»; её id станет `c-night-cherry`.
2. **Допишите украшательства в `config/ModsSite/web/style.css`** — то, чего
   нет в форме панели: фоновые градиенты, узорные подложки, свечения, тени,
   анимации:

```css
/* фон и эффекты для кастомной темы «Ночная вишня» */
[data-theme="c-night-cherry"] {
    --decor-hi: #2A1020;              /* верхний конец градиента страницы */
    --decor-lo: #120611;              /* нижний конец */
    --blob-a: #FF5C8A;                /* цвета трёх светящихся блобов */
    --blob-b: #B197FC;
    --blob-c: #5C6BC0;
    --shadow-card: 0 8px 32px rgba(120, 20, 60, 0.35);
    --focus-ring: 0 0 0 3px rgba(255, 92, 138, 0.18);
}

/* шахматная подложка вместо сетки по умолчанию — как у темы Pixel */
[data-theme="c-night-cherry"] .bg-blob { display: none; }
[data-theme="c-night-cherry"] .bg-grid {
    background-image:
        linear-gradient(45deg, rgba(255, 255, 255, 0.03) 25%, transparent 25%),
        linear-gradient(-45deg, rgba(255, 255, 255, 0.03) 25%, transparent 25%);
    background-size: 42px 42px;
}
```

3. Перезагрузите страницу. Каждый, кто выберет «Ночную вишню» (светлый или
   тёмный вариант), получит ваш дизайн — а палитра по-прежнему идёт из
   панели, так что перекраска позже не потребует лезть в CSS.

Токены, полезные для украшательств: `--decor-hi` / `--decor-lo` (градиент
страницы), `--blob-a` / `--blob-b` / `--blob-c` (три светящихся блоба),
`--shadow-card`, `--shadow-pop`, `--blur`, `--t` / `--t-fast` (тайминги
анимаций). Слои `bg-blob` / `bg-grid` можно перекрасть или скрыть
(`display: none`) — именно так встроенные темы отличаются друг от друга;
загляните в блоки `[data-theme="comic"]`, `[data-theme="pixel"]` и т.п. в
`style.css` — там готовые примеры.

Примечания:

- фоны строятся из **чистого CSS** (градиенты, узоры): модуль раздаёт только
  пять файлов интерфейса, а security-заголовки (CSP) запрещают внешние
  ресурсы — никаких CDN и файлов картинок;
- пара светлый/тёмный работает автоматически: светлые токены живут в базовом
  блоке `[data-theme="c-..."]`, тёмные переопределения — в
  `[data-theme="c-..."][data-mode="dark"]` (образцы — во встроенных блоках
  `style.css`);
- демо-ссылка для быстрых проверок: `?theme=c-night-cherry&mode=dark`.

#### 3. Зашитая тема — как встроенная

Хотите, чтобы тема существовала без панели (например, шла с вашим форком)?
Добавьте полный блок токенов `[data-theme="mytheme"] { ... }` в `style.css`,
запись в `BUILTIN_THEMES` в `app.js` —
`{ id: "mytheme", key: "theme.mytheme", light: "#...", dark: "#...", accent: "#..." }`
(цвета используются для свотча в меню и хрома браузера) — и пару названий
`"theme.mytheme"` в `i18n.js` (ru/en). Ровно так сделаны все шесть
встроенных тем.

### Вкладка «Моды»: фильтры, сортировка, «Отложить»

Над списком модов — панель управления в духе Modrinth:

- **«Опциональные»** и **«Обновления»** — независимые чипы-кнопки со
  счётчиками (можно включить оба — показывается пересечение); состояние
  запоминается в браузере;
- **«Поиск по установленным»** — живой фильтр списка (имя/файл/id, без
  обращений к API) с кнопкой очистки; работает вместе с чипами и
  сортировкой;
- **Сортировка** — отдельный выпадающий список: по умолчанию / А-Я / Я-А;
- в мета-чипах над списком — **селектор загрузчика модпака**
  (Авто / Любой / Fabric / Forge / NeoForge / Quilt): сохранённый загрузчик
  автоматически применяется к поиску и проверкам обновлений;
- под фильтрами — счётчик «Показано: N из M»;
- у мода с доступным обновлением есть кнопка **«Отложить»** (иконка часов):
  последняя версия помечается отложенной — появляется бейдж «отложено», и
  обновление не ставится — ни по отдельности, ни через «Обновить всё».
  Кнопка превращается в «Снять отсрочку»; новая версия у источника снимает
  отсрочку автоматически;
- **«Перезагрузить профили»** — перечитывает конфиги профилей
  (profiles/*.json) с диска: если вы правили `updateOptional`, `modsLoader`,
  `modsGameVersion` и т.п. руками, сайт подхватит это без рестарта сервера
  (после нажатия список профилей и модпак перезагружаются; моды, чьи файлы
  привязаны в `updateOptional`, становятся опциональными).

### Вкладка «Настройки» (админ)

Секция настроек модуля с тремя подтабами:

- **«Обновления»**:
  - **Приоритет источников обновлений** — упорядоченный список
    Modrinth/CurseForge с кнопками ↑↓; недоступный источник (без API-ключа)
    помечается. Порядок действует и на проверки обновлений, и на импорт/
    генерацию метаданных;
  - **«Поведение модпака»** — тумблеры: автопересчёт хэшей, проверка SHA
    после скачивания, разрешение скачивания без хэша, автозависимости,
    синхронизация с `updateOptional`, «опциональные включены по умолчанию»;
    выпадающие списки канала обновлений по умолчанию и TTL кэша API в
    минутах;
  - **«Игнорируемые файлы по категориям»** — шаблоны в стиле .gitignore (по
    одному на строку) отдельно для модов, ресурспаков и шейдеров:
    подходящие файлы и папки никогда не показываются «лишними», не
    импортируются и не опрашиваются на Modrinth/CurseForge. Синтаксис:
    глобы `*` / `?` / `[a-z]`, `**` для любой вложенности, `/` в середине
    или в начале привязывает к корню папки, хвостовой `/` — только каталоги,
    `!шаблон` снимает игнор (побеждает последнее совпавшее правило), `#` —
    комментарий. Для модов по умолчанию игнорируется `.index` — служебная
    папка Sinytra Connector (Fabric-моды на Forge);
  - **«Вывод в консоль сервера»** — уровень логов модуля: `off` (полная
    тишина), `error` (только ошибки), `warn` (ошибки и предупреждения —
    по умолчанию), `all` (всё, включая info/debug). Применяется мгновенно,
    касается только собственных сообщений модуля и никогда не трогает файл
    аудита;
  - сохранение — одна кнопка; изменения сразу пишутся в `Config.json`.
- **«Оформление»** — управление темами (см. «Темы» выше).
- **«Безопасность»** — прежняя вкладка целиком: баны, IP-фильтр, аудит,
  локальные учётки.

### Вкладка «Поиск» (каталог)

Отдельная вкладка для поиска нового — как браузер модов в Prism Launcher:
- **строка поиска** с выбором источника (Modrinth/CurseForge); пустой запрос
  означает режим каталога (просмотр популярных модов);
- **Загрузчик**: чипы «Любой / Fabric / Forge / NeoForge / Quilt»;
- **Версия игры**: поле с подсказками популярных версий; по умолчанию —
  версия выбранного профиля (как в Prism);
- **Сортировка**: релевантность / скачивания / подписки / новизна /
  обновлённые (для CurseForge «подписки» приближённо отображаются как
  популярность — CF их не отдаёт);
- **Категории**: живой список из API источника (Modrinth `/tag/category`,
  CurseForge `/v1/categories`); несколько выбранных объединяются по ИЛИ;
- **пагинация**: 20 карточек на страницу, счётчик «Найдено: N»;
- на каждой карточке — источник, до 3 категорий, скачивания/подписки/дата и
  кнопка **«Добавить»** (админ) или метка «уже в модпаке».

Особенности CurseForge (Core API строже поиска на сайте):
- общее число берётся из `pagination.totalCount` — счётчик и пагинация
  работают так же, как на curseforge.com;
- фильтр загрузчика отправляется только вместе с версией игры (по спецификации
  загрузчик без версии даёт ровно 0 результатов);
- если строгий запрос ничего не нашёл, модуль автоматически пробует мягче и
  честно предупреждает жёлтой плашкой под фильтрами: сначала без загрузчика,
  затем без версии игры (сайт CurseForge при поиске версию тоже не навязывает).
  Категории никогда не ослабляются.

Доступность и детали: клавиатурные фокус-кольца (`:focus-visible`), Esc
закрывает модалки, фокус не покидает открытую модалку, у кнопок-иконок есть
`aria-label`, анимации отключаются при `prefers-reduced-motion`, тосты и
блоки ошибок объявляются как live regions для скринридеров.

## Как это устроено

- **Модпак = ClientProfile.** Файлы модов лежат в
  `updates/<профиль>/mods/` (поддиректория настраивается), состояние — в
  `config/ModsSite/modpacks/<профиль>.json`.
- **Версия игры** берётся из профиля; **загрузчик**
  (fabric/forge/neoforge/quilt) — с 1.0.12 — выбирается селектором на вкладке
  «Моды» (хранится в `modpacks/<профиль>.json` → `loader`), либо из свойств
  профиля (`modsLoader`, `loader`), либо угадывается по имени профиля.
- **Опциональные моды**: отключение мода на уровне модпака убрано —
  «скачано значит нужно», весь модпак и есть состав. Файлы удаляются только
  при удалении мода из модпака; опциональный мод может выключить ИГРОК
  локально — лаунчер его не скачает (исключение через
  `OptionalActionFile.files`).
- **Обновления с переименованием файлов**: каждый мод хранит
  `installedFileName`. При обновлении новый файл скачивается во временный
  (с проверкой SHA-1/SHA-512 из API Modrinth/CurseForge), затем **атомарно
  занимает место старого и только после этого старый файл удаляется по
  сохранённому имени** — переименования не оставляют мусора, а сорвавшаяся
  загрузка, ошибка проверки или сбой диска оставляют прежний рабочий мод
  нетронутым
  (1.1.1: замена только после полной готовности нового файла; временный
  `.part` всегда удаляется).
- **Хэши**: после любого изменения (и по кнопке) вызывается
  `LocalProfilesProvider.sync(...)` — тот же механизм, что у команды `sync`.
- **Зависимости/конфликты** приходят из API источников (Modrinth
  `dependency_type`, CurseForge `relationType`) и привязываются к модам
  модпака по ID проекта.
- **Приоритет источников и перепривязка** (1.0.11). Проверки обновлений идут
  по `mods.updateSourcePriority`: свой источник мода пробуется на его месте в
  порядке, а на более приоритетных источниках установленный файл ищется по
  хэшам (Modrinth — пачкой по SHA-1 `POST /v2/version_files`, CurseForge —
  пачкой по murmur2 `POST /v1/fingerprints/432`). Файл, найденный на более
  приоритетном источнике, перепривязывает запись (source/projectId/name/icon,
  версию установленного файла) — поэтому «лишние» CurseForge-моды плавно
  мигрируют на Modrinth, а моды, положенные в папку руками, получают
  метаданные через «Проверить обновления». Если источник-хозяин недоступен
  или проект удалён, включается тот же фолбэк на следующий источник по
  порядку.
- **«Отложить»** (1.0.11): запись хранит `skippedVersionId` — пока эта версия
  является последней у источника, она не считается обновлением и не ставится
  (включая «Обновить всё»); вышедшая новая версия автоматически возвращает
  мод в список обновлений.

### Опциональные моды: выбор админа и выбор игрока

Существует **две разные системы опциональных модов**, и модуль работает с
обеими:

1. **Уровень админа (модуль)** — чекбокс «Опциональный» на карточке или в
   настройках записи: определяет, может ли игрок отключить мод. Состав при
   этом не меняется: переключателей вкл/выкл больше нет, скачано значит
   нужно.
2. **Уровень игрока (штатная система `updateOptional`)** — чекбоксы в диалоге
   «Настройки» лаунчера: сервер хранит все файлы, клиент пропускает
   выключенные игроком (исключение через `OptionalActionFile.files`).

Опция `mods.syncProfileOptional` (включена по умолчанию) связывает их: для
каждого установленного опционального мода модуль поддерживает запись в
`updateOptional` профиля:

```jsonc
"updateOptional": [
  {
    "name": "sodium",                        // = id мода (slug), стабильно
    "info": "Оптимизация рендера чанков",    // заметка/описание с сайта
    "mark": true,                            // включён игрокам по умолчанию
    "visible": true,
    "actions": [ { "files": { "mods/sodium-fabric-0.6.0.jar": "" }, "type": "file" } ],
    "dependenciesFile": [ { "name": "indium" } ]
  }
]
```

- **Привязка файла обновляется автоматически**: в 5.7.x пути в
  `actions.files` точные (без глобов), поэтому когда обновление переименовывает
  файл, модуль переписывает путь в той же транзакции — до перехэширования.
  Ручные правки не нужны.
- **Выбор игрока переживает обновления**: клиент хранит выбор по `name`, а не
  по имени файла, поэтому `name` фиксируется при создании записи и больше не
  меняется (запоминается в `profileOptionalName` мода).
- `dependenciesFile`/`conflictFile` заполняются из связей модпака — но только
  ссылками на моды, у которых есть собственная запись (иначе клиент получил
  бы null в графе зависимостей).
- Запись удаляется, когда мод становится обязательным или удаляется из
  модпака.

#### Как выбирается name новой записи

Если мода ещё нет в конфиге профиля, имя выбирается автоматически (в порядке
приоритета):

1. **идентификатор из сервиса, откуда скачан мод** — slug Modrinth/CurseForge
   (= `id` мода в модпаке); стабилен между версиями и не требует парсинга
   jar;
2. **modId из самого jar** — если сервис не дал slug (id вида
   `curseforge-12345`): читается из `fabric.mod.json` → `quilt.mod.json` →
   `META-INF/mods.toml` (и `neoforge.mods.toml`) → `mcmod.info`;
3. краевые случаи — синтетический id, человекочитаемое имя из метаданных jar
   или имя файла.

Выбранный источник логируется (`name from service slug` / `jar modId` / ...).
modId из jar сохраняется в модпаке (`installedModId`), а имя мода из
метаданных jar (`installedModName`) используется как запас для `info` записи.

#### Усыновление ручных записей админа

Если в профиле уже есть запись с другим `name`, привязанная к файлу нашего
мода (к текущему ИЛИ **прошлым** именам файла — история хранится в
`previousFileNames`), модуль не дублирует её — он **усыновляет**:

- её привязка перепривязывается при обновлениях (иначе она устарела бы — та
  самая проблема точных путей);
- `name`, `info`, `mark`, `visible` и другие настройки админа не трогаются —
  выбор игроков, хранимый по имени, не теряется;
- при отключении или удалении мода из записи чистятся только его пути; если
  привязок к файлам не осталось и других действий (jvmArgs и т.п.) нет,
  запись удаляется целиком, иначе живёт с оставшимися файлами;
- зависимости других модов ссылаются на фактическое имя записи (включая
  усыновлённое), а не на id модпака.

**Правила владения**: запись принадлежит модулю, если её `name` совпадает с
`profileOptionalName`/`id` мода из модпака — такие записи ведутся целиком
(кроме ручных move-привязок с непустым значением — они сохраняются). Поля
`mark`/`visible`/`info` существующей записи никогда не перезаписываются
(задаются один раз при создании). Не нужны чекбоксы игрокам? Поставьте
`mods.syncProfileOptional: false`.

#### Зависимости и конфликты: редактор связей в настройках записи

В настройках записи (кнопка «Настройки» у любой записи; обязательному
ресурспаку/шейдеру опциональность даёт чекбокс «Опциональный») — блок
«Зависимости и конфликты»:

- **цели — только опциональные моды** этого модпака (обязательные всегда
  включены, ссылаться на них бессмысленно; члены одной опциональной группы
  тоже скрыты — группа делит один переключатель);
- у каждого кандидата два чекбокса: **«Зависимость»** и **«Конфликт»**;
  отмеченный бокс создаёт связь, **оба сняты — удаляют** (раньше был неудобный
  мульти-селект). Зависимость и конфликт на одной паре взаимоисключающи;
- конфликты **симметричны**: снятие конфликта у одного мода снимает его у
  обоих;
- **вычищенные связи остаются вычищенными**: у связи, удалённой админом,
  появляется «надгробие» — авто-импорт из API («Проверить обновления»,
  «Разрешить зависимости») никогда не вернёт её; повторная отметка снимает
  надгробие, и авто-импорт снова работает. То же про связи профиля: список,
  вычищенный на сайте, никогда не заполняется из профиля заново (заполнение
  происходит один раз, в пустой список);
- списки пишутся в профиль (`dependenciesFile`/`conflictFile` записей
  `updateOptional`) при каждом сохранении настроек — лаунчер применяет их,
  когда игрок щёлкает чекбоксы.

## Авторизация

Настройка `auth.mode`:

| Режим | Локальные учётки (конфиг) | Учётки лаунчера |
|---|---|---|
| `hybrid` (по умолчанию) | да | да |
| `local` | да | нет |
| `launcher` | нет | да |

**Локальные учётки** — список `accounts` в конфиге. Пароль можно вписать
открытым текстом в поле `password` — при старте он **автоматически заменится
на PBKDF2-хэш**. Управление: команда `mods user ...`.

**Учётки лаунчера** проверяются через auth-провайдера (`authId`, пусто =
пара по умолчанию). Кто из них админ, решает
`launcherAuth.adminCheck.type`:

- `permissions` (по умолчанию) — админ, если у учётки есть право `mods.admin`
  или роль `modsadmin` (настраивается: `permission`, `role`). В
  MySQL/PostgreSQL-провайдерах GravitLauncher это колонка `permissions`/
  `roles` таблицы пользователей (например, `"perms": ["mods.admin"]`).
- `sql` — **ваш собственный SQL-запрос**, например к колонке `isAdmin` (любое
  имя колонки — это просто часть вашего запроса):

```json
"launcherAuth": {
  "authId": "",
  "adminCheck": {
    "type": "sql",
    "sql": {
      "url": "jdbc:mysql://127.0.0.1:3306/launcher?useSSL=false&allowPublicKeyRetrieval=true&serverTimezone=UTC",
      "user": "launcher",
      "password": "пароль от БД",
      "query": "SELECT isAdmin FROM users WHERE username = ?",
      "params": ["{login}"],
      "trueValues": ["1", "true", "t", "yes", "y", "admin"]
    }
  },
  "treatNonAdminAs": "viewer"
}
```

`url` — обычный JDBC-URL. Для MySQL:
`jdbc:mysql://хост:3306/имя_базы?useSSL=false&allowPublicKeyRetrieval=true&serverTimezone=UTC`.
Драйвер (`mysql-connector-j`) уже есть в `lib/` сборки LaunchServer — ничего
дополнительно ставить не надо. Оставьте `url` пустым, чтобы модуль переиспользовал
настройки соединения из SQL-провайдера лаунчера (тогда `user`/`password` тоже
не нужны).

Подстановки в `params`: `{login}`, `{uuid}`, `{username}`. Первый столбец
первой строки сравнивается с `trueValues` (без учёта регистра).

**Важно**: настройки `auth`, `launcherAuth` и `superAdmins` применяются при
живой перезагрузке конфига так же, как и остальные (правка Config.json на
диске или `mods reload`) — перезапуск сервера не нужен. В версиях до 1.1.2
эти настройки после reload не подхватывались (выполнялся старый SQL-запрос,
и админы БД ошибочно виделись как viewer).

**Все админы БД видятся как viewer — что проверить** (запустите
`mods checkadmin <логин>` — команда печатает каждый шаг и текст ошибки):

1. `adminCheck.type` действительно `"sql"` (по умолчанию `permissions` —
   тогда смотрятся колонки perms/roles, а не ваша колонка);
2. запрос возвращает строку: 0 строк = не то имя таблицы/колонки в WHERE;
3. сырой первый столбец совпадает с `trueValues` (для INT/BIT обычно `1` —
   оно в списке по умолчанию; MySQL-драйвер может вернуть и `true` —
   тоже в списке);
4. число `?` в запросе равно длине `params`;
5. в логе сервера ищите `sql adminCheck failed` — там стек полной ошибки
   (например `Unknown column 'isAdmin'` при несовпадении имени колонки).

Кроме того: если суперадмин включал для логина пометку «наблюдатель»
(«Безопасность → Роли», файл `admin-roles.json`), она действует ПОВЕРХ
результата проверки БД — снимается кнопкой «Вернуть роль».

- `treatNonAdminAs`: `viewer` (только чтение) или `deny` (вход запрещён).
- `auth.onlyAdminsCanLogin: true` — сайт пускает **только админов** (локальные
  не-админы и обычные учётки лаунчера отвергаются).
- **TOTP 2FA**: для локальных учёток — `mods user totp <логин>` (секрет и
  ссылка otpauth:// печатаются в консоль). Для учёток лаунчера — карта
  `launcherAuth.extraTotp`: `{"логин": "base32-секрет"}`.

### Живые роли и суперадмин

Роли **пересчитываются на каждом запросе**, а не запоминаются при входе:

- назначили админа в БД лаунчера (или в правах) — перезагрузили страницу —
  он уже админ; сняли — права исчезают при следующем же запросе (без разлогина);
- назначили/сменили роль в `accounts` конфиг-файла — подхватывается сразу:
  конфиг-файл модуля перечитывается автоматически при изменении на диске
  (аккаунты, роли, суперадмины, домены — без `mods reload` и без перезапуска);
- удалили/выключили локальную учётку — админ-права снимаются немедленно.

**Суперадмин** — логины задаются ТОЛЬКО вручную в конфиг-файле модуля:

```json
"superAdmins": ["ваш_логин"]
```

Действует независимо от того, откуда пришёл аккаунт — из БД лаунчера или из
локальной записи. Суперадмин имеет все права админа и единственный видит
под-вкладку **«Безопасность → Роли»**, где для любого админа можно включить
пометку **«наблюдатель» (viewer)**:

- пометка хранится в отдельном файле `config/ModsSite/admin-roles.json`;
- **запись админа в конфиге или в БД лаунчера не изменяется** — оверрайд
  снимается так же легко (кнопка «Вернуть роль»);
- суперадмина понизить нельзя (защита `superadmin_protected`);
- смена роли применяется у пользователя без разлогина — на его следующем
  запросе; в аудит пишутся `admin_role_override` и `superadmin_denied`.

## Безопасность

Всё включается/выключается независимо в конфиге.

| Механизм | Настройка | Поведение |
|---|---|---|
| Бан IP за перебор | `security` | N неудач в окне → бан; **длительность эскалирует** по `banScheduleMinutes` (5 мин → 15 мин → 1 ч → 6 ч → 24 ч); после истечения бана рецидив сдвигает на следующий уровень (сброс уровня после `levelDecayHours` чистого времени) |
| Блокировка логина | `security.accountLock` | M неудач для логина (с любого IP) → эскалирующая блокировка |
| Белый список | `whitelist` + `mods whitelist add <ip\|cidr>` | IP/CIDR, которые **никогда не банятся** (и не попадают под rate limit) |
| Чёрный список | `blacklist` + `mods blacklist add <ip\|cidr>` | IP/CIDR, которым **всегда отказано** (403) |
| Rate limit | `rateLimit` | Раздельные лимиты: общий API (240/мин) и вход (30/мин) на IP |
| TOTP 2FA | `auth.totpEnabled` | Для учёток с секретом |
| CSRF | — (всегда вкл для POST) | У каждой сессии свой `X-Mods-CSRF`; POST без него — 403 |
| Cookies | `web.cookieSecure/cookieSameSite` | HttpOnly, SameSite=Lax, Secure — автоматически на HTTPS |
| Security-заголовки | `web.securityHeaders` | CSP, X-Frame-Options, X-Content-Type-Options, Referrer-Policy |
| Аудит | `audit` | JSONL-журнал: входы/неудачи/баны/правки состава/IP-фильтр; ротация по размеру |
| Пароли | — | PBKDF2-SHA256 (210k итераций), сравнение за константное время |

Состояние защиты хранится в `config/ModsSite/ipfilter.json` (переживает
рестарты); сессии — в `config/ModsSite/sessions.json` (на диске только
SHA-256-хэши токенов).

Разбан: `mods unban <ip>`, `mods unban account <логин>` или кнопки в панели
«Безопасность».

## HTTP и HTTPS

В GravitLauncher 5.7.x сам LaunchServer слушает **HTTP** (настраивается в
`LaunchServer.json` → `netty.binds`); TLS обычно терминируется обратным
прокси. Модуль полностью поддерживает оба варианта:

- все ссылки интерфейса **относительные** — работает на любых
  хосте/порту/протоколе;
- флаг cookie `Secure`: `web.cookieSecure = auto` (по фактическому HTTPS
  соединения) / `always` / `never`;
- `web.trustProxyHeaders = auto` — доверяет `X-Forwarded-For`/
  `X-Forwarded-Proto`, если у LaunchServer включён `netty.ipForwarding`
  (можно принудительно `true`/`false`);
- `web.httpsRedirectUrl` — опциональный редирект HTTP→HTTPS (для прокси).

Пример nginx (проксирует и сайт, и API лаунчера):

```nginx
server {
    listen 443 ssl http2;
    server_name launcher.example.com;
    # ssl_certificate ...; ssl_certificate_key ...;

    location / {
        proxy_pass http://127.0.0.1:9274;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_set_header Upgrade $http_upgrade;      # websocket лаунчера
        proxy_set_header Connection "upgrade";
        proxy_read_timeout 3600s;
    }
}
```

и в `LaunchServer.json` включите:

```json
"netty": { "ipForwarding": true, ... }
```

— тогда модуль видит реальные IP клиентов за прокси.

### Один сайт, два адреса: ip/mods/ и корень домена

По умолчанию сайт живёт по пути `/mods` — например,
`http://192.0.2.10:9274/mods/`. Если на сервер указывает домен (A-запись на
IP сервера, порты 80/443 через прокси или прямой порт), его можно добавить в
`web.siteDomains` — и сайт откроется В КОРНЕ этого домена:

- `http://192.0.2.10:9274/mods/` — продолжает работать как раньше;
- `http://mods.example.com/` — тот же сайт в корне домена;
- оба адреса работают одновременно и ведут на один сайт;
- доменов можно перечислить несколько (до 16, через настройки сайта или
  конфиг: по одному на строку или через запятую);
- порт в заголовке Host игнорируется: пишите домен без порта;
- домен принимается в любом виде — `mods.example.com`,
  `https://mods.example.com/`, `mods.example.com:443` нормализуются к одному
  и тому же хосту.

Если сайт в корне домена не открывается, чаще всего причина одна из двух:

1. **Обратный прокси (nginx, Caddy, Cloudflare) подменяет заголовок Host.**
   По умолчанию `proxy_pass` отправляет proxируемый адрес в Host, и модуль
   видит `Host: 127.0.0.1:9274` вместо домена — совпадения нет (типичный
   случай «на localhost работало, на реальном домене нет»). Лечение:

   ```nginx
   location / {
       proxy_pass http://127.0.0.1:9274;
       proxy_set_header Host $host;
       proxy_set_header X-Forwarded-Host $host;
       proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
   }
   ```

   Модуль также проверяет `X-Forwarded-Host` (первое значение), когда
   доверяет прокси-заголовкам (`web.trustProxyHeaders` = `true`/`auto` +
   netty `ipForwarding`), — достаточно любого из двух заголовков.

2. **Домена просто нет в `web.siteDomains`.** Модуль пишет WARN (не чаще
   раза в минуту на хост), когда на «сайтоподобный» путь (`/`, статика)
   приходит Host вне списка, — в логе виден точный полученный Host, и
   причина становится очевидной.

Важно: в корне обслуживаются только перечисленные домены. Запросы в корень
любого другого хоста (например, `http://192.0.2.10:9274/` со стороны
лаунчера — профили и скачивание файлов) уходят дальше по конвейеру
LaunchServer нетронутыми — файловый сервер и websocket лаунчера работают как
прежде.

Техническая деталь: путь `/api` на сервере занят websocket'ом лаунчера,
поэтому API сайта всегда доступно по `/mods/api/...` (на любом хосте, включая
корневой домен); UI сам определяет рабочий базовый адрес API при старте
пробным запросом `health` — настраивать ничего не нужно.

Пример конфига:

```jsonc
"web": {
    ...
    "siteDomains": ["mods.example.com", "mods2.example.net"]
}
```

После правки конфига — `mods reload`; через настройки сайта применяется
мгновенно.

## Консольные команды

Все команды регистрируются в консоли LaunchServer под корневой командой
`mods`:

```
mods status                              — статус модуля
mods user add <логин> <пароль> (admin|viewer)
mods user remove <логин>
mods user list                           — локальные учётки
mods user pass <логин> <пароль>          — смена пароля (убивает сессии)
mods user role <логин> (admin|viewer)
mods user enable|disable <логин>
mods user totp <логин>                   — включить 2FA (печатает секрет/ссылку)
mods user totpoff <логин>
mods whitelist add|remove|list [ip|cidr] — никогда не банить
mods blacklist add|remove|list [ip|cidr] — всегда отказывать
mods bans                                — активные баны IP и блокировки логинов
mods unban <ip> | account <логин>
mods rehash [profile|all]                — пересчитать хэши (кнопка на сайте)
mods check [profile]                     — проверить обновления модов
mods checkadmin <логин>                  — диагностика признака админа у учётки
                                           лаунчера (permissions/sql): печатает
                                           запрос, сырое значение из БД, текст
                                           SQL-ошибки, итог: ADMIN / NOT admin
mods reload                              — перечитать конфиг модуля
mods site                                — статус сайта (вкл/выкл)
mods site on                             — включить сайт (алиас: enable)
mods site off                            — ВЫКЛЮЧИТЬ сайт: все запросы /mods
                                           (страницы и API) отвечают 503 "Site closed",
                                           все веб-сессии сбрасываются. Лаунчер
                                           и раздача профилей НЕ затрагиваются.
                                           Состояние сохраняется в конфиге между рестартами
mods sessions list|clear                 — активные веб-сессии
mods web                                 — статус файлов сайта (config/ModsSite/web)
mods web restore                         — перезаписать ВСЕ файлы сайта из jar
mods curseforge test [version]           — проверка ключа CF + пробные поиски (своя версия игры)
mods curseforge categories               — дамп категорий модов CF (что покажут фильтры)
mods curseforge search <запрос> [version] [loader] — живой поиск по CF тем же кодом, что и сайт
mods curseforge fingerprint <файл|папка>... — murmur2-отпечатки ваших jar + живой запрос к CF:
                                            знает ли он эти файлы (диагностика «мод есть на CF,
                                            но импорт пометил его локальным»)
mods profile optionals [profile]         — ДИАГНОСТИКА ОПЦИОНАЛЬНЫХ МОДОВ: как модуль видит
                                            updateOptional (в памяти + прямо из profile.json),
                                            какие форматы распознаны и почему конкретный мод
                                            остаётся «обязательным» (что не совпало)
```

## Конфигурация (все параметры)

Файл: `config/ModsSite/Config.json` (создаётся при первом старте; можно
править руками, затем `mods reload` или рестарт).

```jsonc
{
  "enabled": true,                      // главный выключатель модуля

  "web": {
    "uiEnabled": true,                  // раздавать веб-интерфейс
    "apiEnabled": true,                 // REST API (false = только консоль)
    "title": "Mods Manager",
    "defaultLang": "ru",                // ru | en (пользователь может переключить)
    "cookieSecure": "auto",             // auto | always | never
    "cookieSameSite": "Lax",
    "trustProxyHeaders": "auto",        // auto (по netty.ipForwarding) | true | false
    "httpsRedirectUrl": "",             // например "https://mods.example.com"
    "securityHeaders": true,
    "cspExtra": "",
    "siteDomains": []                   // домены, обслуживающие сайт в "/" (например "mods.example.com")
  },

  "auth": {
    "mode": "hybrid",                   // hybrid | local | launcher
    "cookieName": "mods_session",
    "sessionTtlMinutes": 720,
    "onlyAdminsCanLogin": false,        // пускать только админов
    "totpEnabled": true,                // спрашивать TOTP, если задан секрет
    "maxSessionsPerIp": 0,              // 0 = без лимита
    "maxFieldLength": 256
  },

  "launcherAuth": {
    "authId": "",                       // id auth-пары из LaunchServer.json ("" = пара по умолчанию)
    "adminCheck": {
      "type": "permissions",            // permissions | sql | none
      "permission": "mods.admin",
      "role": "modsadmin",
      "sql": {                          // для type=sql
        "url": "",                      // "" = переиспользовать SQL-провайдер лаунчера
        "user": "", "password": "",
        "query": "SELECT isAdmin FROM users WHERE username = ?",
        "params": ["{login}"],
        "trueValues": ["1", "true", "t", "yes", "y", "admin"]
      }
    },
    "treatNonAdminAs": "viewer",        // viewer | deny
    "extraTotp": { }                    // TOTP-секреты для учёток лаунчера
  },

  "accounts": [                         // локальные учётки (пароль -> хэш при старте)
    { "login": "admin", "passwordHash": "pbkdf2_sha256$...", "role": "admin", "enabled": true }
  ],

  "superAdmins": [],                     // суперадмины — ВРУЧНУЮ в этом файле: логин, из БД или локальной записи;
                                         // управляют ролями админов в «Безопасность → Роли»

  "security": {
    "enabled": true,                    // баны IP за неудачные входы
```

## Бекапы

В версии 1.1.0 появилась **система бекапов** профилей (вкладка «Бекапы»,
только админ). Бекап — **настоящий `.mrpack`** (формат модпаков Modrinth),
который лежит в `config/ModsSite/backups/<профиль>/<uuid>.mrpack`:

- **Структура mrpack**: в корне `modrinth.index.json` (`formatVersion: 1`,
  `game: "minecraft"`, `files[]` с `path`, `hashes` (sha1 + sha512), `env`,
  `downloads`, `fileSize` и `dependencies` с `minecraft`) и `overrides/` для
  локальных файлов. Бекап можно открыть в Modrinth App или любом другом
  mrpack-совместимом инструменте — и модуль же умеет его восстанавливать.
- **Умное хранение контента**: моды/ресурспаки/шейдеры с привязкой к
  Modrinth/CurseForge НЕ архивируются — каждый становится записью `files[]`
  с прямой ссылкой скачивания (CDN Modrinth / редирект CurseForge); при
  восстановлении РОВНО тот же файл скачивается заново и проверяется по
  записанным sha1/sha512. Если прямая ссылка не сработала — версия
  перезапрашивается по id через API источника (fallback). Файлы без привязки
  (локальные моды, конфиги) уходят в `overrides/`.
- **Сайдкар модуля**: `modssite.index.json` внутри архива (сторонние
  mrpack-инструменты его игнорируют) хранит id/имя/дату бекапа, список
  папок бекапа и снапшот модпака
  (`config/ModsSite/modpacks/<профиль>.json`); при восстановлении возвращается
  на место, `updateOptional` пересогласовывается, хэши профиля
  пересчитываются (если включён `mods.autoRehash`).
- **Папки бекапа** выбираются **галочками прямо во вкладке «Бекапы»** —
  список строится из папок, реально существующих в папке сборки профиля
  (`updates/<профиль>/`), плюс стандартные папки контента. Пусто (кнопка
  «По умолчанию») = `mods`, `resourcepacks`, `shaderpacks` с учётом
  переопределений; можно отметить и `config`, `scripts` и т.п. (до 16).
- Напротив каждого бекапа пишется его **размер**, сверху — **общий размер
  всех бекапов**. Имя по умолчанию — дата и время, переименовывается.
  Кнопка **«Заморозить»** защищает бекап от случайного удаления
  (замороженные также никогда не удаляются авто-очисткой).
- Авто-очистка: при превышении `backup.maxBackups` (30) на профиль удаляются
  самые старые НЕзамороженные СВОИ бекапы (замороженные и чужие mrpack
  квоту не занимают).
- Восстановление возвращает выбранные папки и состав модпака к состоянию
  бекапа (честный снапшот): привязанный контент заново скачивается с
  Modrinth/CurseForge, файлы этих папок, добавленные после бекапа,
  удаляются (ignore-шаблоны и временные файлы не трогаются).
  Файлы с `env.client = "unsupported"` (серверный контент) пропускаются —
  профиль LaunchServer — клиентская сборка. Восстановление асинхронное —
  вкладка опрашивает активную задачу и показывает тост с итогом
  (файлы / скачано / удалено / ошибки, каждая ошибка также пишется в лог).
- Бекап можно скачать из интерфейса как `.mrpack` (до 128 МБ; большие —
  забирайте напрямую из `config/ModsSite/backups/` на сервере).

**Чужие mrpack**: в папку бекапов профиля (`config/ModsSite/backups/<профиль>/`)
можно положить ЛЮБОЙ валидный `.mrpack` — в том числе скачанный с Modrinth
пакет ДРУГОЙ сборки. Он появится в списке после открытия вкладки (мета
строится из `modrinth.index.json`; имя файла с пробелами/юникодом приводится
к безопасному) и восстанавливается как обычный бекап: `overrides/` и
`client-overrides/` распаковываются в папку сборки, `files[]` скачиваются
с проверкой sha1/sha512, папки покрытия (верхние сегменты путей манифеста)
очищаются от лишнего — сборка становится равной чужому пакету. Состояние
модпака собирается из манифеста: файлы с ссылками cdn.modrinth.com /
curseforge.com получают привязки к источнику, остальные — локальные записи
(потом их можно принять «импортом осиротевших»). Если пакет собран под
другую версию Minecraft — в итоговом сообщении будет предупреждение.
Замороженные и чужие mrpack не удаляются авто-очисткой (только вручную).

Безопасность: архивы пишутся атомарно; при восстановлении валидируется
каждый путь из манифеста и каждая запись `overrides/` (никаких `..` и
абсолютных путей — из папки профиля не выйти), симлинки не архивируются
никогда, прямые загрузки разрешены только с https-хостов из allowlist
(CDN Modrinth, зеркала CurseForge, GitHub), ограничены по размеру и
проверяются по хэшам, все операции с бекапами пишутся в аудит.

Конфиг (`mods.backup.*` в Config.json): `enabled` (true), `maxBackups` (30),
`maxFiles` (5000), `maxTotalMb` (2048).

## Прогресс обновления (1.1.1)

`POST /mods/api/mods/update` («Обновить всё» / «Обновить» у мода) и
`POST /mods/api/mods/apply` («Применить состав») больше не держат запрос,
пока не докачается всё. Сервер запускает **фоновую задачу** и отвечает
сразу; панель открывает окно прогресса и опрашивает
`GET /mods/api/mods/progress` каждые 0,7 с — всегда видно:

- текущая **фаза**: подготовка → проверка обновлений (`12/40`) →
  скачивание → пересчёт хэшей (rehash) → готово;
- **строка на каждый мод**: ожидает / проверка / скачивается (с живыми
  байтами, например `3.4 / 7.1 MiB`) / обновлён (версия) / пропущен /
  отменён / ошибка;
- общий прогресс-бар (`завершено / всего`).

На профиле работает только одна фоновая задача: повторный запуск даёт
409 `update_in_progress`, и панель просто прицепляется к бегущей задаче.
Пока задача держит лок профиля, остальные меняющие профиль эндпоинты
(check/add/remove/skip/import/clean/rehash/…) отвечают 409
`update_in_progress` вместо молчаливого ожидания; сам список модов
(`GET /mods/api/mods`) во время обновления остаётся доступным (чтение без
лока — сохранения атомарны) и несёт снимок задачи: после перезагрузки
страницы окно статуса открывается само. Окно прогресса можно свернуть —
задача продолжит работу, а итоговый тост «Обновлено: X/Y» всё равно появится.

**Остановка обновления (1.1.1).** В окне статуса есть кнопка **«Остановить»**
(`POST /mods/api/mods/update/stop`): уже начатые скачивания докачиваются
и устанавливаются, не начатые — отменяются (помечаются «отменён» и исчезают
из очереди), итоговый тост честно показывает, сколько докачано и сколько
отменено.

**Отказоустойчивая установка (1.1.1).** Файл мода заменяется только после
того, как свежая версия полностью скачана и проверена по хэшу, а сама замена —
атомарный rename (где поддерживает файловая система; там, где не
поддерживается, — со страховочной копией и восстановлением при сбое).
Предыдущий файл удаляется только после того, как новый уже на месте, — поэтому
оборвавшееся скачивание, несовпадение хэша, таймаут или сбой диска не могут
оставить «мода вообще нет»: старая версия продолжает работать. Опциональные
моды идут тем же путём, а зависшая задача одного мода больше не прячет
результаты остальных в пакете.
